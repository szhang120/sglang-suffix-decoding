# A linear SuffixDecoding adaptation for SGLang

**Status: initial GPU correctness gate passed; performance unverified.** This project has not reproduced the paper's speedups. It contains source pins, a CPU implementation reused from the authors, SGLang integration code, passing host checks and reproducible GPU experiment scripts. Modal executes the model on one H100 80GB HBM3 (driver580.95.05). The final linear configuration passes the30-case exact-ID gate; profiling and benchmarks are pending.

## Why suffix speculation can help

A target model ordinarily computes one new token per decode forward. If a CPU cache proposes a likely continuation, a causal target forward can evaluate several positions together. For greedy generation, candidate token j is accepted only if the target prediction conditioned on the accepted prefix matches it. Stop at the first mismatch, emit the target correction, and discard the remaining candidates. If all candidates match, emit a target bonus token. Acceptance changes the number of sequential model calls, while target verification still pays for every input row it computes.

The [SuffixDecoding paper, v3](https://arxiv.org/html/2411.04975v3) uses a per-request prompt/output suffix tree and a global prior-output tree. Matching suffix length controls speculation budget; occurrence statistics estimate continuation likelihood. Score sums estimated acceptance probabilities, selecting a candidate across matches and caches. This project starts with its linear greedy variant. Its public workload covers open-ended requests and refinement, where limited repetition can legitimately yield weak or negative gains.

The adapted implementation deliberately retains both caches. A current prompt can contain a phrase that the model copies, while previously generated responses can reveal a template absent from the new prompt. Combining the two is useful, but neither cache is a guarantee of future target output. All cache suggestions remain untrusted drafts until the target verifies them.

## Integration and KV accounting

The SGLang v0.5.21 NGRAM worker already contains model-free draft verification, greedy prefix acceptance and KV movement. Reusing those routines makes the integration smaller and preserves scheduler conventions. `SUFFIX` routes through the NGRAM scheduler family with a distinct CPU proposer. No vLLM model execution occurs.

The target verify input has k+1 rows: the last committed output token followed by k proposals. That committed token is the pending input root; it has been emitted but must still be processed into target KV. Its logits predict proposal 1, later rows predict successive candidates, and the final row provides the full-match bonus. On rejection, only the processed input prefix corresponding to accepted outputs is settled. The new correction remains pending until the next forward. “Emitted tokens” and “processed KV positions” are therefore offset; confusing them is a common off-by-one error.

`NgramVerifyInput` carries actual width and a linear causal mask. The inherited greedy tree verifier operates on this chain. The inherited KV mover settles accepted input locations, and result stride tells the scheduler how to unpack output rows. Only scheduler-committed output is inserted into suffix caches on the next proposal or completion hook. Stop-truncated output uses `output_ids_through_stop`. Prefill-only completion has an explicit hook, and abort discards its cached response.

The author implementation is vendored as a standalone C++20/nanobind module with Apache-2.0 notices. One Python wrapper bug is repaired: the unspecified proposal cap uses `max_tree_depth`, not the nonexistent `max_depth` attribute. Native matching and tie behavior remain unchanged, including the native loop's exclusive upper bound on context length. The SGLang worker limits lookup context to 64 tokens and global retention to 128 requests.

## Adaptivity must change executed rows

A fixed CUDA graph can still execute a full padded tensor after a proposer returns fewer meaningful tokens. In that situation adaptivity improves acceptance statistics but may save little GPU computation. This candidate disables graphs and overlap, slices preallocated storage to k+1 actual rows, updates verifier/backend width consistently, and forwards only those rows. A zero-length proposal executes one target row.

The scheduler still reserves the maximum KV capacity. Reservation does not imply a padded target forward; it is a separate memory cost. Conversely, a smaller mask proves neither smaller GEMMs nor lower kernel time. Correlating CPU verification spans with actual GPU launches establishes which work changes. Possible costs include eager kernel launches, CPU suffix lookup, cache synchronization and full-prefix mask construction. These can outweigh a reduction in target forwards on short or unpredictable continuations.

A first controlled profile uses a126-token prompt and three randomized trials at widths1/2/4/8/16/33; all18 outputs exactly match ordinary generation. Median summed GPU kernel time is12.93ms at one row and14.00ms at33 rows (7.7% lower at one row). KV-store grids change from2 to66 blocks per layer, and argmax from19 to528 blocks, establishing some actual reduced GPU work. The attention grid stays one query tile: its64-row tile pads all tested widths. Its64-key loop also crosses a context boundary:126+1 takes two key tiles,126+33 three. This measurement cannot establish a uniform per-row compute saving. Aligned128/512-context controls are prepared.

The same trace exposes a full1.09GB LM-head transpose copy on each forward. In deterministic mode, SGLang’s `_mm_dtype_compat` makes `weight.T` contiguous before selecting the FP32-output Triton matmul, even though that kernel supports explicit strides. The copy kernel takes about4.8ms in this profile. A guarded local change keeps the original weight view and the same Triton calculation; it passes the30-case token/KV gate. Native BF16 logits are not a working substitute: both speculators fail six of30 cases. The final study therefore retains FP32 logits with the copy removed, applied equally to every baseline. The final trace contains the head matmul without the large contiguous/clone/copy operations and without the corresponding GPU copy kernel. Cross-image timing differences are diagnostic, not a randomized estimate of this fix’s serving speedup.

The final controlled study tests 54 requests, three randomized trials per width/context, all exactly matching ordinary output IDs. It includes aligned contexts to control the 64-key tile boundary:

| Input context tokens | One-row median kernel sum | 33-row median kernel sum | Reduction at one row |
|---:|---:|---:|---:|
| 126 | 7.83ms | 8.94ms | 12.4% |
| 128 | 7.98ms | 8.99ms | 11.2% |
| 512 | 8.86ms | 10.26ms | 13.6% |

These are sums of correlated kernel durations in an instrumented first verification, not request wall latency or hardware FLOP counts. At all three contexts, KV-store grids grow from `[2,1,1]` to `[66,1,1]` and argmax from `[1,19,1]` to `[33,16,1]`. Attention keeps `[1,28,1]`, and the persistent head matmul keeps `[132,1,1]`. Shorter proposals therefore reduce some actual GPU execution, but major kernels retain internal padding. A 33-fold row reduction produces a much smaller time reduction. Full samples, kernel names/grids and trace hashes are in `results/width-probe-final/`.

## Evidence obtained locally

Ten tests pass on Python 3.12.14 / Apple Silicon macOS. They cover local/global separation, FIFO eviction and request-ID reuse, adaptive proposal bounds/native tree integrity, 100 randomized oracle greedy generations, actual worker host shape contracts, output caps, non-ingestion of proposed tails and stop-truncated completion. The worker contract tests stub SGLang's target; they do not execute GPU sampling or KV movement.

The saved CPU microbenchmark contains 12,800 draft lookups over synthetic periodic integer tokens. Median lookup time in this run is **4.25 microseconds**. This is a per-lookup measurement on a small artificial corpus and cannot establish target-model throughput, a paper timing comparison, or GPU speedup. Raw samples and platform information are in `results/cpu-profile.jsonl` and `results/cpu-profile-summary.json`.

A Ubuntu 24.04 x86_64/Python 3.12 binary-wheel dependency resolution succeeds with 212 exact hashed packages. That checks package metadata consistency. The first Modal installation caught a CUDA-tile wheel/stub hash mismatch; a direct NVIDIA wheel verified against the public index now replaces the downloader stub, with a fresh resolver cache. The failed setup log is retained. The locked image installs successfully, builds Rust/native extensions, passes ten Linux tests and pip check, imports SGLang, and executes Qwen with all three decoding modes. This validates the text-inference path exercised here; it does not validate every optional binary module. A clean integration patch applies to the pinned SGLang source; syntax and local host tests pass.

## Preliminary GPU correctness evidence

Default BF16 FlashInfer execution produced the same final-token divergence in both NGRAM and SUFFIX: ordinary chose ID1380 and both speculators ID11 at output position127 of the tides prompt, across three repetitions. The other 27 cases matched. Enabling common batch-invariant operations and setting both FlashInfer split sizes to4096 made all30 NGRAM cases match. SUFFIX matches29/30; only the warm-cache tides repetition diverges at position113, while cold and flushed repetitions match. All raw failed runs are retained. Neither finding establishes a KV bug or harmless numerical drift; target-logit and acceptance diagnostics are required before drawing that distinction. An FP32-output LM head alone does not repair the divergence: all three SUFFIX tides repetitions now differ at113, with ordinary top-two gap0.010645 and suffix gaps0.024614 (cold/flushed) and0.045656 (warm) favoring the other token. Actual GPU-generated positions, retrieval links, emitted argmax prefix, acceptance length and advanced sequence length all pass their independent linear-chain assertions. This narrows the investigation, but does not prove KV contents or intermediate hidden-state equivalence. Common deterministic Triton attention matches all30 SUFFIX cases; branching NGRAM differs on one warm length128 case at position96 with ordinary top-two gap0.015711. Linear NGRAM PROB breadth1 matches all30 cases, matching the suffix topology; this is an explicit baseline change. The direct-KV snapshot diagnostic initially indexed one extra layer and failed before SUFFIX generation; that diagnostic error is corrected, with raw failure preserved. The final Triton/FP32-logit/linear-NGRAM configuration passes all30 exact-ID cases for both speculators. Across416 suffix verify rounds, independent assertions validate GPU positions, linear tree links, argmax acceptance/correction, sequence advancement, bitwise preservation of every existing key/value prefix and accepted input-slot identity. These checks establish the exercised path, not bitwise equality for every possible prompt. They do not by themselves explain which earlier kernel caused the numerical differences. Benchmarks have not run.

## GPU experiment contract

The current candidate uses Qwen2.5-7B-Instruct at the locked model revision on one H100 80GB, BF16, TP1, Triton attention, page1, batch1, batch-invariant operations, FP32-output logits and4096 decode split size. FlashInfer attempts are retained as failed configurations. The final measured settings will be frozen after the correctness gate. Every baseline disables graphs, overlap and radix prefix caching. This isolates the algorithm in a common eager configuration; it cannot characterize the fastest production SGLang configuration.

The public Spec-Bench subset contains the first four prompts per category in original order: 52 questions across 13 categories. Freeze tokenizer IDs and baseline-derived second-turn refinement inputs. Measure independent requests, sequential initial/refinement pairs, and repeated identical prompts separately. Within a block, prior outputs become available causally; never seed the cache with future ground-truth answers. Warm kernel execution precedes a cache reset. Linear NGRAM PROB uses33 slots, breadth1 and trie depth64; suffix has a 33-slot capacity and adaptive actual width. Ablations remove the match-length bound or disable the global cache.

Run exact token-ID checks before timings. Save five rotated-order trials, raw request timings/outputs, workload hash, resolved server settings, installed package versions and GPU state. Profile in separate runs so instrumentation synchronization does not contaminate timing results. Any output mismatch is a failure to investigate, even if text looks similar. Numerical differences between decode and verification shapes are a possible cause, not a reason to silently accept divergence.

## Relationship to the original experiments

The paper's single-GPU comparison uses Llama-3.1-8B-Instruct, batch one and H100; its end-to-end OpenHands experiment uses a different model and four-way tensor parallelism. This project uses Qwen2.5-7B-Instruct, SGLang and a small public Spec-Bench subset plus refinement. It does not have the proprietary AgenticSQL workload or reproduce a live SWE-Bench agent trajectory. See [the paper's evaluation methodology](https://arxiv.org/html/2411.04975v3#S4.SS1) for its setup.

Current outcome: **performance behavior unresolved**, rather than positive or negative reproduction. Report independent/refinement/repetition results separately once measured. A gain restricted to repeated identical prompts would demonstrate an upper bound, not broad agentic workload value. No gain on open-ended prompts would be consistent with weak repetition; causality requires profiler evidence before attributing a slowdown to a particular systems cost.
